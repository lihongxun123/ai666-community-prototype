# 研究站内容组织、生产与 C/B 端闭环审查

日期：2026-09-24｜状态：审查发现与待讨论建议，不新增已确认产品范围

## 结论

研究站已经解释了用户怎么看、怎么用，也提出了作者供稿、编辑编选、资源维护和圈子回应的分工。但这些尚未收束为明确的内容对象、生产权限、维护责任和 C/B 端操作。继续只细化 C 端页面，会把这些未决问题埋进卡片、详情和跳转之中，增加后续返工。

已确认的移动端架构可以保留，不必推翻；下一阶段应先将**内容组织、生产与 B 端承接一起讨论**，再恢复逐页原型深化。不能从现有页面或概念图推导已经具备完整内容供给能力，也不能把增加后台页面当作作者、专业判断或维护人员已经到位。

本次检查研究站实际源码、移动端需求底稿和相关真实 B 端本地代码；未重新调研外部竞品、测试生产系统、查询用户数据或验证后端接口。结论针对内容业务闭环，不是视觉审查或线上功能验收。

## 2. 五个会影响改版的关键缺口

### 2.1 四类详情不是完整的内容生产模型

移动端底稿已确认作品、帖子、官方教程、AI 应用四类详情。这足以约束页面承接，但资源层仍缺归属：工作流、画布项目、模板、Prompt、Skill、参考文件应该作为内容附件、可独立维护的资源，还是应用的一部分？

“案例”也可能是一篇讲解作品过程的帖子或教程，不必直接新增第五种发布表单。反过来，工作流文件若只是一篇帖子的附件，后续换版、依赖失效和多篇教程引用它时，会缺少统一维护位置。

**建议先分清五个层面，具体实现待定：**

| 层面 | 回答的问题 | 例子 |
| --- | --- | --- |
| 内容 | 用户读什么、看什么、讨论什么 | 作品、经验帖、案例讲解、教程 |
| 应用与资源 | 用户运行、下载或继续编辑什么 | 可运行应用、工作流、画布项目、模板 |
| 组织关系 | 为什么把这些内容放在一起 | 专题编排、圈子归属、分类、内容引用 |
| 来源与责任 | 谁创作、谁发布、谁对更新负责 | 普通作者、合作作者、官方编辑、资源维护者 |
| 展示与使用 | 用什么形式看，在什么设备操作 | 图文、视频、对照；手机运行、PC 编辑 |

这不是要求新增五个 C 端栏目或五套后台系统；需要的是每个对象身份与关系清楚。页面可以复用，文件与版本也可以先采用轻量管理。

### 2.2 “官方教程”尚未覆盖所有深度内容的来源

研究站欢迎作者贡献教程、过程、案例和方法；当前底稿只确定了官方教程独立发布管理，以及普通用户轻发布。合作作者提交深度教程、用户经验被精选或改编成官方教程，分别缺少明确路径。

不能让“内容足够深”自动等于“官方内容”，也不能因进入精选而改变作者归属。下一轮需确定：作者经验先作为帖子发布是否足够；是否需要结构化教程投稿；官方编辑如何收稿和返修；授权、署名、更新责任由谁承接。暂不默认开放所有人直接发布官方教程。

### 2.3 AI 应用的生产包含工程工作

可运行的 AI 应用与介绍某工具的文章不同。应用至少需要明确运行方式、输入输出、依赖与设备适配、测试结果和维护者。站内运行、外部跳转、下载后在工具中运行也不是同一种承诺。

“运营填写名称、封面、介绍”不能生成一个可用应用。研究站的六类应用概念表达了使用差异，但没有确定谁构建、谁接入、谁测试、谁上线或下线。

建议优先讨论官方／定向合作资源由技术人员核验、编辑整理后上架的受控路径；是否开放普通用户自助提交或发布应用，另行决策。不能从此建议推导已经有应用市场、执行引擎或自由接入能力。

### 2.4 组织与生产角色没有落到具体动作

研究站已有“平台编排为主，定向合作与自然投稿并行”的建议，但缺少每种内容最小交付、返修条件、生产入口和负责人的组合。

建议区分三条生产路径，而不是要求所有投稿填同一张深度表单：

| 路径 | 提交者提供什么 | 谁完成后续工作 | 用户端对应 |
| --- | --- | --- | --- |
| 普通表达 | 作品、想法或具体问题，关联信息选填 | 作者发布；平台按规则审核治理 | 首页作品、社区帖子和讨论 |
| 编辑组织的深度内容 | 合作作者的过程、条件、取舍及可公开材料 | 编辑核料、返修、整理、署名与专题编排；专业问题由相应人员核验 | 深度案例、教程、专题内容 |
| 应用与资源 | 可运行配置或文件、示例、依赖、许可及维护说明 | 技术或维护者核验可用性；编辑组织呈现；授权负责人决定上架 | 应用详情、资源使用和 PC 引导 |

这些是业务分工建议，不预设三个新部门。一个人可以兼任多种角色，但专业核验与维护工作不能被“平台负责”四字省略。供给合作用于取得材料，与真实用户是否愿意持续使用需要分别验证。

### 2.5 公开、推荐与可用状态尚未联动

内容合规通过、编辑决定推荐、资源技术可用、是否适合手机是不同判断。把它们归成一个“审核通过”会导致应用已失效但仍在首页推荐，或者撤推荐时误删原帖。

需要讨论最小状态和权限：谁决定公开、谁收录专题、谁排序推荐、谁能暂停应用使用，原作者更改或删除后如何影响引用。

建议区分“原内容状态”“专题／展示位关系”“应用或资源可用状态”。失效时按影响暂停操作或撤推荐，必要的介绍与讨论可以保留；内容违规或撤回时按规则停止相关公开引用。具体状态名、自动联动程度和权限尚未定版。

## 3. B 端已有基础与需要补齐的业务能力

真实 B 端本地代码已有作品管理、帖子管理与审核精选、教程编辑及发布、分类话题、Banner、金刚区和其他展示位配置。不能说 B 端从零开始；也不能据此断言生产接口与新需求都已具备。

特别注意三个概念不等价：

- **话题标签不等于专题编排**：已读话题表单是名称、关联分类、排序等；多类型内容分组、收录理由、编排与整体预览是另一个业务范围。
- **教程板块不等于圈子**：圈子还有加入关系、圈内发布、主持与治理；教程分组不自动具备这些能力。
- **爆款模板不等于深度 AI 应用**：已读模板管理基于作品及 `is_hot_template` 标识，不证明已具备任意工作流接入、资源版本或应用可用性管理。

建议按下列业务能力讨论 B 端，而不是先列菜单页面：

| 必要能力 | 对应 C 端承诺 | 当前证据与下一步 |
| --- | --- | --- |
| 内容编辑、审核、上下架 | 作品、帖子、官方教程及状态反馈 | 现有本地页面与调用可参考；补深度稿件、署名和关联方式的差异 |
| 专题编排与分发 | 专题按主题组织，首页按位置推荐 | 核对如何跨类型收录、分组排序和预览；不拿标签配置替代 |
| 应用与资源维护 | 实际可用入口、设备限制、版本与失效说明 | 先确定对象与运行边界，再做最小登记、核验、上下架与影响查询 |
| 圈子运营与内容治理 | 公开圈子、可选归属、持续交流 | 明确建圈权限、主持职责、内容归属和治理动作；本轮未完成全仓／后端能力审计 |
| 治理与内部维护 | 违规内容由平台独立审核治理，内部确认失效后退出推荐 | 本轮取消用户举报、纠错及故障反馈全流程，保留内部维护责任和正常错误状态 |
| 效果观察 | 浏览与创作并重、内容持续有用 | 关联曝光、详情、尝试／使用、具体反馈与复访；外部工具无法观测时明确缺口 |

作者邀约、稿酬约定、生产排期等可以先用简表与人工协作。首轮不必建设完整作者 CRM、自动任务分配、复杂审批流或结算平台。

## 4. 一条内容生产到维护的示例

以下仅用“商品图案例”说明结构，不重新确定电商优先，也不代表已有素材、应用或合作作者。

1. **确定需求与选题**：编辑确认专题要帮助用户解决哪类任务，盘点现有案例和缺口。
2. **取得材料**：作者提供可公开成果、必要过程与条件；涉及文件复用时另核使用许可。普通用户只发作品也可以，不承担全部交付。
3. **分别生产**：案例内容保持作者署名；教程讲清做法；应用或工作流有对应维护者和可用性核验。几者可独立提供，不要求凑齐。
4. **审核与编排**：内容按规则进入公开状态；编辑选择收录到专题、设置顺序和呈现位置，指向同一原内容。
5. **消费与使用**：手机用户看案例，若应用手机可用则尝试；需要工作流或画布编辑时引导 PC。是否收藏、发布或提问由用户决定。
6. **反馈与修订**：具体问题关联原内容或资源；主持分流，维护者核查。教程或资源更新时记录必要更正，专题继续引用正确对象。
7. **失效与复盘**：暂停失效操作或推荐，保留适当说明；观察真实使用、问题处理和再次贡献，而不是只统计发帖数和点赞。

必须区分：一篇内容发布成功，只完成生产的一步；被收录、被使用、获得反馈和持续维护不是自动发生的。

## 5. 研究站需要澄清的历史口径

1. `content-plan` 将电商营销列为建议重点；`lib/task-freshness.json` 的 2026-09-20 记录暂缓缺少近期原图、失败及修正对照的旧商品图样板，并停止用“换背景困难”支持电商优先。`freshness/page.tsx` 同时明确，内容配置及电商样板按当前方案页组织。因此不是取消电商研究方向，也不是两份材料直接互相否定；需要重做的是旧样板及其论证。本轮移动底稿尚未确认实际生产优先级，不能把研究建议直接转成生产排期。
2. 较早内容体系强调任务路径；本轮用户已经确认浏览与创作并重、作品可单纯表达。生产门槛必须分层，不能要求每个普通作品附方法、资源或验证报告。
3. 融合结构页仍有手动保存、教程归帖子等早期写法；新移动底稿已确认自动生成记录、官方教程独立承接。当前研究站仍有未同步内容，本轮仅审查，不批量改写历史方案或改变已确认决定。

## 6. 接下来的讨论顺序

暂停继续逐条确认 C 端细节，先用四轮确定闭环；每轮都同时写清作者／运营／C 端／B 端的动作。

| 顺序 | 要决定的问题 | 最小产物 |
| --- | --- | --- |
| 1. 内容对象与关联 | 深度案例、教程、应用、工作流、画布等是什么关系，哪些需要独立维护 | 内容对象及关系图，不预设新增 C 端入口 |
| 2. 生产来源与职责 | 用户能直接发什么，合作作者交什么，官方制作什么，谁核验和维护 | 每类内容一条生产路径及最低交付要求 |
| 3. B 端与发布维护 | 谁编排、推荐、审核、暂停、修订；现有后台复用哪里 | C/B 动作与状态对照，缺口分为产品待定和技术待核 |
| 4. 代表性样本 | 选一项有可用材料的任务，把生产—编排—使用—反馈走通 | 一份可走查的内容样本和双方原型；真实招募、生产写入、运行额度另按授权执行 |

先解决第 1 轮，不立即决定全部字段、排期或全部后台页面。优先级依据真实可取得的材料与维护能力，不以历史电商示例或概念图数量决定。
